# Perseus Studio 整体设计审计

日期：2026-10-20 晚间。对象：当前本地工作树，包含前序尚未提交的修复。以下保留修复前的研究、反例与计划。

**实施更新（2026-10-21）**：用户授权后的实际改动、最终回归与逐项未完成边界见 [DESIGN_AUDIT_REMEDIATION.md](DESIGN_AUDIT_REMEDIATION.md)。A07 OS 隔离、A09 完整跨资源事务、A14 全量状态解耦等仍未全部关闭；下文“当前行为”及“未修改实例”仅指原审计快照，不是本轮交付状态。

## 结论

项目有可继续维护的 React / Go / SQLite 基础，不需要推倒重写。但业务规则还不够可靠：一些本应由工具协议、明确错误类型、运行状态决定的行为，散落在关键词判断、提示词、兼容分支和共享状态中。文件拆短和测试通过没有消除这些问题。

最值得先处理的是：**展示文本被升级为写文件动作、正常说明被当成任务失败、错误类型丢失、终态恢复仍保留临时消息**。命令执行缺少宿主隔离是另一条独立的高风险边界，公开多用户部署前必须处理。

本轮既审原代码，也审前序修复。没有修改生产运行代码，没有重启或升级 8080，没有调用付费模型，没有推送。故障注入仅使用临时目录、独立 SQLite 数据库和本地模拟供应商；命令隔离探针只读取测试自己创建的工作区外标记文件。探针源和输出归档在 `_local_artifacts/design-audit-20261020/`，临时 Go 探针已从常规测试目录移除。

## 验证方法与边界

- 跟踪请求准入 → provider 响应 → 动作分派 → 参数验证 → 工具执行 → 修改验证/账本 → 完成判定 → SSE/快照恢复。
- 对不合理的猜测设计反例，而非机械统计 `Contains` 或正则数量。
- Go 探针共 10 个顶层测试，另有 2 个 Node 消息合并探针，故意按期望契约断言，暴露当前行为；这些失败是审计证据，不能写成“新增回归全部通过”。
- 移除临时 Go 探针后的现有基线：Go `test ./...` 全部通过；前端单测 **149/149** 通过；UI、结构门禁通过，扫描 135 个前端文件和 280 个 Go 生产文件。
- 本轮未执行完整浏览器故障注入、Linux/race/容器运行测试和长时间压力测试。下面分别注明实测与静态结论，不将局部证明扩大为所有模型或所有场景结论。
- 8080 只读就绪检查正常，running=0、queued=0；本轮未写手动数据库或用户工作区。

证据文件：`probes.log`、`integration-probes.log`、`frontend-probes.log`、`go-baseline.log`、`unit-baseline.log`、`structure-metrics.json`。探针源分别保存在 `ai-probes.go.txt`、`workspace-probes.go.txt`、`integration-probes.go.txt`、`frontend-probes.mjs`。重放 Go 探针时应复制到对应包的独立测试文件，只运行 `TestDesignAudit*` 并在结束后移除；不要在用户数据库运行。

## 问题清单

P0：不可信多用户使用前的阻断条件。P1：会影响动作正确性、数据或恢复，近期优先。P2：契约、维护性、性能或运维问题，分阶段处理。优先级不等于已被外部利用。

### A01 / P1：正文中的补丁示例会真的执行

证据：`backend/internal/ai/model_response_dispatcher.go:7`、`agent_text_patch.go:163`、`agent_runtime.go:40`；**独立数据库端到端复现**。

分派器先从正文中抽取补丁，再检查结构化工具调用。不区分代码围栏里的讲解示例和真正的动作意图；抽取到补丁时还会丢掉同一响应中的原工具调用。

探针用户请求“只讲解补丁格式，不要创建或修改文件”，模拟模型返回“下面只是格式示例，请勿执行”及围栏补丁。运行器实际创建了 `example-only.txt`，内容 `demo\n`。另一个纯分派探针确认，示例会替换原本的 `read_workspace_text` 调用。

这是展示通道与动作通道混用，不能靠再匹配“示例”“勿执行”修好。建议以结构化 `apply_workspace_patch` 为正常编辑入口；正文补丁兼容应成为明确、可关闭、范围受限的协议模式，不能无条件覆盖结构化调用。迁移时保留现有正常编辑回归，并增加“讲解/引用/围栏示例绝不落盘”反例。

### A02 / P1：完成判定在猜自然语言含义

证据：`backend/internal/ai/agent_completion.go:90`、`:119`、`:182`；**函数级复现**。

两个反例：

- 合法答复“apply_workspace_patch 是用于修改文件的工具。”被判成泄露内部编辑协议，拒绝完成。
- 已有后端验证的成功写入后，答复“文件已保存，尚未运行测试。”仍被认定在报告 workspace 写入未完成。原因是“文件”与“尚未”在整段内容中分别命中，程序没有理解“尚未”指的是测试。

当前规则也把 `failed_items` 与必须发生过工具失败绑定，难以自然表达未运行验证、范围外工作或部分完成。对可恢复工具失败，一律要求继续修复，也缺少清楚的 blocked/partial 退出语义。

建议：完成状态由结构化 outcome、工具事实、已验证变更和未完成事项决定；正文允许解释工具名、代码和限制。保留“不能凭文字宣称文件已修改”的后端验证，去掉用词汇猜完成真假的硬拦截。失败、部分完成和成功应能诚实结束，不能迫使模型继续写文件来通过终态检查。

### A03 / P1：错误在多层中被转成文字再重新猜类型

证据：`backend/internal/ai/tool_diagnostics.go:117`、`agent_runtime.go:273`、`action_selection_state.go:70`、`backend/internal/api/conversation_run_diagnostics.go:142`；**函数级复现**。

同一个 `workspace.ErrTrashManagedOnly`，直接传给分类器时得到 `workspace_path_policy`；经过运行器当前采用的 `error → string → fmt.Errorf` 过程后，变成 `tool_execution_failed`。即使底层已经有明确错误类型，调用链仍把它丢掉。

分类不只影响显示，还决定 recoverable、完成拦截、目录条件是否满足及重复错误处理。API 又通过中文提示判断 run 分类；修改文案或翻译可能改变诊断结果。供应商侧虽已有 `ProviderResponseError` 与 HTTP 状态分类，部分路径仍退化为自由文本匹配，并非所有错误都已有统一类型。

建议保留原始 error 链，统一 `code/category/retryability/side_effect_state/details`；用 `errors.Is/As` 和结构化状态做决定。国际化文案只在展示边界生成。外部中转确实可能只有文字错误，可以在单一适配层保留保守兜底，并记录分类依据，不能把它扩散到本地工具和 API 状态机。

### A04 / P1：模型显示名称会改变执行能力判断

证据：`backend/internal/ai/provider_profile.go:33`、`:124`；**函数级复现**。

相同协议 `openai`、相同模型 `grok-4.3`，仅把显示名称从“我的模型”改成“替代 Claude 的模型”，profile 从 `standard` 变成 `claude_like`，默认上下文从 128000 变成 200000，单次文件内容预算从 18000 变成 14000 字符。

显示名称、BaseURL 和 ModelID 被混合匹配；`gpt-5`、`gemini-2` 等宽泛名称还被统一推定为固定窗口。中转别名和新版本会使这种猜测失效。显式 `ContextWindowTokens` 有优先权，这是已有的正确边界，但不能阻止显示名称改变其他 profile 限制。

建议建立显式 provider 能力配置：上下文、消息布局、工具协议、参数支持和预算。模型名识别只做有来源的初始建议，显示名不参与决策，用户覆盖优先。前序 Grok 合并 system 消息的兼容逻辑有实际故障依据，但也应迁移到明确能力配置，以支持模型别名。

### A05 / P1：终态快照恢复可能保留旧临时消息

证据：`src/hooks/chatMessageMerge.js:3`、`:36`，调用方 `chatRunStream.js:84`、`:148`、`:320`；**纯消息合并反例复现，尚未完整浏览器断网复现**。

合并函数为防止旧快照覆盖活跃流，按正文长度和前缀保留本地 pending 消息。这在流式阶段有用途，但终态补读仍调用同一套规则：

- 本地较长临时回复遇到服务端较短的 completed 回复，仍留下旧正文和 pending。
- 服务端已经丢弃、快照中不再存在的草稿，仍被保留并与最终消息并列。

正常收到 `assistant_message_completed/discarded` 会走专门处理，不能说所有正常完成都坏了。缺口在连接反复失败后轮询终态和快照收敛；当前缺少显式“这是终态权威快照”的合并语义。

建议消息以 run/message 身份、状态、序号或 revision 合并；活跃增量与终态 reconciliation 分开。终态必须清除对应 run 的 pending、过期草稿和旧预览，同时保留尚未提交的用户输入。补充断网跨完成、草稿撤回、较短最终答复、多次重连浏览器回归。

### A06 / P1：补丁容错没有充分区分内容语义

证据：`backend/internal/ai/tools_exec_workspace_patch_match.go:157`；**函数级复现**。

匹配依次尝试原文、去尾空白、去首尾空白、Unicode 标点/空白归一化，每一级要求唯一匹配。它不是按关键词猜位置；候选行的关键词打分只用于失败提示，这部分不应误判。

真正风险是容错层级可能改变代码语义。内容为 `if enabled:\n    allow()\n`，补丁旧行误写成无缩进的 `allow()`，新行为无缩进的 `deny()`；当前仍成功生成 `if enabled:\ndeny()\n`。工具验证确认的是生成内容已落盘，不能发现 Python 缩进语法已坏。

建议代码默认严格处理语义空白和引号；非精确容错需要明确策略与 `match_mode` 元数据，必要时让模型重读并修正，不能静默把排版差异当作无意义差异。不要删除唯一性检查，也不要把候选提示升级为实际定位器。

### A07 / 条件 P0：命令黑名单不构成权限隔离

证据：`backend/internal/workspace/command.go:18`、`:140`；**真实子进程、测试自有临时文件复现**。这是前序已公开的未解决边界，本轮补充了直接证据。

`echo "docker documentation"` 因包含 docker 被拒；不含禁词的 `[IO.File]::ReadAllText(...)` 可以读取工作区外由测试创建的标记文件。cwd 只决定起始目录；环境白名单减少凭据继承，但没有约束服务身份能访问的磁盘和网络。

对个人本机、可信用户，这属于明确的能力风险；对不可信多用户，不能把该执行器当作隔离边界。应使用受限 worker/OS 隔离、限定挂载、网络与资源配额，或在隔离完成前限制此工具的可用范围。不能通过继续添加语言命令禁词宣称修复。现有黑名单可作额外提示，不应单独承担授权。

### A08 / P1：事件或消息持久化失败，没有立即反馈给执行所有者

证据：`backend/internal/api/conversation_run_execute.go:47`、`:332`、`:405`；**静态调用链确认，未做 SQLite trigger 故障注入**。

`recordPersistenceErr` 保存首个错误，后续日志/消息回调停止写入，但不会取消传给 `GenerateReply` 的 context，也不能通过回调返回 error；主要在模型执行返回后才统一读取错误。若仅消息/事件写入失败而工具账本仍可写，运行器可能继续消耗模型请求或执行后续工具，最终 UI 只得到失败。

工具账本自身的严格失败保护已经存在，不能说所有数据库失败都会继续写。需要补齐的是 API 持久化回调到运行所有者的失败传播。

建议用专属执行 context 和明确失败原因，在持久化失败时停止新的模型/工具准入，再进行有界清理。保留 persistence failure 原因，不能因内部 cancel 将它误报为“用户取消”。验收用独立库只阻断某一类事件写入，证明失败后的下一次工具不执行。

### A09 / P1：多文件修改仍不是崩溃事务

证据：`backend/internal/ai/workspace_patch_commit.go:10`、`workspace_patch_rollback.go`、`backend/internal/workspace/file_write.go`；**现有机制静态复核，未新增杀进程测试**。

当前有逐文件 CAS、原子替换、版本和尽力回滚，已比直接覆盖安全；但多个文件分步提交，回滚计划主要保存在内存。进程在两次落盘之间退出，会留下部分文件已改的工作区；DB 账本/checkpoint 与文件系统也不共享事务。工具描述中的 “applies the patch atomically” 容易给出超出实现边界的保证。

建议先修正文档/工具契约，再增加持久变更计划、每步状态、重启核验和可恢复提交；整轮快照与逐文件撤销应明确分开。故障验收应覆盖第 N 个写入/移动/回收之后崩溃，而非只测试正常返回 error 的回滚。

### A10 / P2：Schema 校验只做到表面

证据：`backend/internal/ai/tool_argument_validation.go:14`、`:77`；**真实工具 schema 的函数级复现**。

`read_workspace_files.paths=["a.md",42]` 能通过 schema 校验。后台任务 expected_outputs 内的无效 enum、缺失 description，以及 suggested_steps 中的布尔值，也能通过。实现只验证顶层 required、顶层类型和字符串枚举，不递归 items/properties，也未落实额外属性约束。

部分后续 struct 解码和业务验证仍会拒绝这些参数，所以这是验证边界不完整，不是“所有非法参数都会执行”。但错误出现层级、恢复提示和对模型宣告的契约不一致。

建议明确支持的 schema 子集并递归验证，或使用可维护的验证库；从同一 ToolSpec 产生 schema、调度与验证，避免不同语言/协议重复定义。契约测试要真正投递畸形值；仅比较 OpenAI/Anthropic schema 相同，或在 AST 中找到 dispatch 字符串，不足以验证运行时契约。

### A11 / P2：工具调用成功与命令业务结果缺少统一区分

证据：`backend/internal/workspace/command.go`、`backend/internal/ai/tools_exec_command.go`、`tools_executor.go:60`、`tools_verify_workspace.go:112`；**独立数据库实际执行 `exit 23` 复现**。

命令结果包含 exit_code=23，但外层 ToolEvent.status 仍为 success。调用成功表示拿到了命令结果，这个定义可以成立；问题是恢复/完成逻辑主要消费统一 success，缺少统一的 execution_outcome 和 expected_exit_codes 契约。文件变化验证也不等于构建或测试成功。

不要简单把所有非零返回码都变成不可恢复错误，例如 grep/rg 的未匹配也可能是预期结果。建议分清 invocation、process outcome、artifact verification，UI 展示退出码，模型必须根据实际输出报告验证情况；超时和取消必须独立表示。

### A12 / P2：文件引用与操作权限范围混在一起

证据：`backend/internal/ai/tool_scope.go`，尤其 `:99`；**静态复核，未做完整交互复现**。

附件引用自动激活只允许这些路径的范围；但“作为上下文附加一个文件”未必表示“不能新建关联文件或读取依赖”。另一方面，这张路径提取表覆盖显式文件工具，不覆盖 command。它既可能限制正常跨文件任务，也不能作为全工具权限边界。

建议将 reference/context 与 allowed mutation/read scope 分成明确概念。限制范围应有用户可理解的授权语义，并由所有执行入口共同执行；否则只能称为降低误操作的产品规则。不能增加对“这些文件”等中文句子的猜测来补足权限模型。

### A13 / P2：命令前后全树扫描不受命令超时完整约束

证据：`backend/internal/workspace/command.go:18`、`command_snapshot.go:23`；**静态确认，未在大工作区压测**。

命令前后遍历未被忽略的文件并计算哈希，成本随文件总量增长。命令 timeout context 在首次快照之后创建，快照扫描自身没有 context 取消检查、累计字节/时间预算。`hashFileForCommandSnapshot` 遇到读错返回空 hash，也缺少明确的“变更探测不完整”结果。

建议对扫描独立设截止时间和数据量预算，传播读失败，明确 excluded/incomplete。后续再考虑有界索引、文件 watcher 或受控命令 worker 的变更收集。扫描结果只能说明观察到的差异，不能据此承诺所有宿主副作用均可恢复。

### A14 / P2：文件短了，但核心状态仍高度耦合

证据：`src/hooks/useChatState.js`、`backend/internal/ai/agent_runtime_types.go`、`agent_entrypoints.go`、`agent_loop_guard.go`；**结构计数与静态复核**。

当前聊天 facade 自身有 17 个 useState、10 个 useRef；agentRuntime 有 40 行非空字段声明。这些数字本身不是 bug，但说明“每个文件不到 450 行”不能证明状态简单。多个 action 共享大批 setter/ref；前后端事件常以自由字符串/map 传播，协议分支和运行状态同步依赖人工维护。两个协议入口还有大段相同运行器初始化。

循环进展指纹主要看已变更路径/满足的目录条件；对路径内容变化、只读研究进展表达有限，有成功修改后多条 loop guard 分支又不再触发。它不是统一的任务进展模型；总轮数/工具预算仍是最终上限，不能误称无限执行。

建议先为现有状态写合法转换和不变量，再逐步引入 reducer/明确事件类型、缩小 action 依赖、复用运行器初始化；不要先换框架或继续按行数机械拆文件。每次迁移保持外部协议兼容并添加状态序列反例。

### A15 / P2：重试虽有上限，仍欠缺统一的等待与总预算语义

证据：`backend/internal/ai/provider_sdk.go:24`、`provider_retry.go:91`、`agent_recovery.go`；**静态确认**。

SDK 内置重试已设为 0，请求重试和检查点恢复均有上限，这些做法应保留；不能泛称当前无限重试。需要改善的是供应商等待和整轮预算：`Retry-After: 60` 在默认 MaxDelay=5秒时被截短为 5秒，仍可能过早重复请求；多个阶段的请求重试、流回退、上下文修复、检查点恢复会放大总请求次数，但没有同样清楚的整轮费用/耗时预算契约。

建议尊重 Retry-After；超过前台等待预算时明确暂停或安排后续，而不是提前重发。请求级与运行级统一记录剩余次数、累计耗时/费用和是否已产生副作用。用固定模拟供应商验证 429/503、长 Retry-After、流中断及取消，不必依赖真实模型额度。

### A16 / P2：测试与健康评价还不够能说明产品是否可靠

证据：本轮反例与全绿基线并存；`docs/PROJECT_HEALTH_SCORECARD.md`、`.github/workflows/ci.yml`；**本轮实际运行及静态复核**。

已有契约、取消、CAS、恢复、编辑器保护测试和浏览器测试是真实资产，不应删掉。但大量测试偏向提示词约定和正常流程，缺少“正文讲解绝不执行”“真实终态压过临时 UI”“改变文案不改变状态”等反例。按代码行数和目录布局自评 9.6/10，不能代表运行正确率。

建议用能力/故障矩阵代替当前可靠性数字评分：每项标明已实现、模拟验证、真实验证、尚未验证。将本轮探针逐个转成修复后的长期回归，增加事件序列、崩溃阶段、坏参数和并发覆盖；记录可重放的脱敏 provider 样本。Linux/race/容器测试需要实际执行证据，不能仅因 CI 文件写了步骤就视为通过。

## 哪些判断可以保留

不是所有字符串判断都需要重构：

| 用途 | 判断 |
|---|---|
| SSE 的 `data:`、补丁明确语法标记、文件扩展名、HTTP content-type | 合理协议/格式解析；应检查边界，不必消灭字符串 |
| 路径分隔符与目录前缀边界、状态枚举集合 | 合理确定性验证；不要替换为模型猜测 |
| Markdown 疑似格式问题、未知扩展语法保守预览 | 可作为辅助提示；目前需用户确认、先保存核验再发 Agent 的边界应保留 |
| 失败补丁的相似候选提示 | 可帮助重读；当前候选打分不直接决定落盘位置 |
| 外部 provider 无结构化码时的文字兜底 | 可保留在单一适配边界，标注不确定性，不能压过明确类型/状态 |
| 正文词汇决定是否完成、显示名决定能力、命令禁词承担隔离 | 应整改；这些是在用可变文本决定业务事实或权限 |

## 前序修复的自审

1. JSON `SetEscapeHTML(false)` 用于模型文本中的 JSON，保留外层请求编码，且没有全局反转义。这项调整有针对性，前序已验证字面 `\u0026` 不被改写；它改善模型看原文的质量，不代表原 JSON 编码非法。
2. 不匹配补丁拒绝落盘、CAS 和回滚保护有价值，不应为了“能改文件”而放松位置和版本核验。
3. 补丁提示词和专门失败文案帮助模型纠错，但仍经过 A03 的文字分类；这是缓解，不是统一错误契约的完成。
4. 正文补丁兼容虽让部分供应商更容易编辑，也保留了 A01 的误执行风险；前序修复没有解决这条边界，必须纳入下一阶段。
5. 扩展 Markdown 保守预览、惯用格式诊断属于数据保护策略；它们不能承诺覆盖全部语法。以后支持更多语法，应通过解析/序列化的往返保真测试扩展，不能靠去掉保护实现“都能编辑”。

## 渐进整改顺序与验收

这轮不建议大搬目录，也不建议把所有启发式改成另一套更长的正则。

| 阶段 | 改动 | 必须交付的验证 |
|---|---|---|
| 1：动作与终态契约 | A01/A02/A06；结构化编辑主通道，兼容模式明确；终态取工具事实；语义空白不静默放宽 | 示例/引用不落盘，正常两协议编辑仍通过，诚实限制可完成，Python 缩进/引号差异明确拒绝或标记 |
| 2：错误与执行控制 | A03/A08/A10/A11；错误贯穿到底，持久失败停止新动作，递归验证参数，区分调用与命令结果 | 改文案/包装/语言不改变错误类别；仅事件表故障后无下一工具；嵌套坏参数到不了执行器；非零预期退出码有明确语义 |
| 3：恢复与 provider 能力 | A04/A05/A12/A14/A15；终态快照权威合并，能力显式配置，状态不变量与统一运行预算 | 改显示名不影响请求；丢完成/撤回事件可收敛；跨文件引用语义清晰；重连/取消/长限流等待不重复副作用 |
| 4：隔离与崩溃一致性 | A07/A09/A13；受限 worker、持久变更计划、扫描/磁盘等资源配额 | 工作区外测试路径/跨用户/网络策略；每阶段杀进程恢复；大树取消和磁盘耗尽；匹配 DB/文件备份恢复演练 |
| 持续：质量证据 | A16；行为矩阵、负例、provider 样本、平台验证 | 每项标示验证级别，先复现再修；不再用历史高分替代可靠性结论 |

阶段 1–3 可以沿现有模块逐项实施；公开不可信多用户部署时，阶段 4 的隔离部分应提前成为准入门槛。结构边界若要调整，应先按 `STRUCTURE_STANDARDS.md` 更新对应架构文档。

成熟项目的可复用经验是动作/权限/副作用/恢复的契约和失败证据，而非单纯工具数量或提示词长度。已核对过的固定版本研究见 [MATURE_AGENT_COMPARISON.md](MATURE_AGENT_COMPARISON.md)；本轮没有重新抓取或宣称审计那些项目的全部最新代码。

本审计覆盖关键链路与代表性反例，未穷尽所有 UI、插件、模型和平台组合。原报告形成时以上均待实施；后续修复状态以整改报告中的行为证据为准，不能把既有基线通过或探针复现写成缺陷已修复。
