F01 回归还发现相关恢复缺口：刷新后的任务虽然能显示历史，但输入框未恢复运行中状态。现在从持久运行身份恢复排队、停止和补充指令能力，在没有当前页面事件流时轮询任务进展；新增“刷新后停止”回归。

## 输入持久性与边界

- 使用排队消息 ID 与稳定请求身份 `pending:{id}`，不根据正文关键词猜测是否发送。受理响应丢失后按原请求查询恢复，多页面重试不会生成第二个运行。
- 内容、原模型与思考模式由已保存记录决定；替换或删除后的旧 ID 不能提交。转为运行中补充指令时，持久事件与消费也在同一事务提交；重试不会再次应用。
- 存储失败回滚后保留输入。删除已经受理的消息返回冲突，避免把“删除排队项”误当成停止已经开始的任务。
- 查询、更新和发送均按认证用户隔离；自动发送失败采用退避，当前任务失败或取消不自动追加下一轮。
- 自动调度仍由已连接的工作台页面驱动。关闭所有页面时，服务端保留输入，重新连接后继续调度；本轮没有实现独立后台发件 worker。
- 延续现有交互，一条可替换跟进只包含文本及原模型/思考模式，不宣称新增多条附件发件队列或未发送草稿跨重启持久化。
