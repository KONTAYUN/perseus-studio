## 确认的问题

### F01 / P1：刷新页面丢失“结束后发送”的排队消息

复现：在 Agent 运行时输入普通跟进，界面显示“当前任务结束后自动发送”；刷新并返回同一会话。排队消息不再显示，原任务成功完成后也没有发送后续消息。两次独立真实运行复现，服务端会话消息中均没有该跟进。

影响：用户已经提交到排队界面的要求静默丢失；运行本身能恢复显示，不能据此认为待发送内容也已恢复。

定位：`src/hooks/useChatState.js:54` 的 `pendingRunMessage` 仅为 React 内存状态，没有可恢复的持久队列。页面重建后无法还原。

证据：`10-queued-before-reload.png`、`10-queued-after-reload.png`、`reconnect-messages.json`、`reconnect-events.json`、`14-queue-before.png`、`14-queue-after.png`、`queue-refresh-repeat.json`；用例 `E01-queued-input-reload` 及其 repeat。

建议：将待发内容按用户、会话、消息身份持久化；优先服务端接收队列，明确等待、发送、取消与失败状态，提交使用幂等身份。若采用浏览器 outbox，也需刷新恢复、发送确认与重复投递保护。回归覆盖刷新、切会话、原任务成功/失败/取消、重复重连和再次发送。不能仅补一个“刷新会丢失”的提示。

### F02 / P1：压缩上下文清空未发送的输入草稿

复现：在输入框保留一段未发送文字，点击上下文使用量并执行“压缩上下文”。草稿由 33 字符变为空，文字没有作为用户消息发送。重复两次：首次实际压缩 26 条消息；第二次服务端返回“不需要压缩”，同样丢草稿。

影响：与发送消息无关的操作会直接丢失用户改稿意见。

定位：`src/hooks/chatCompactionActions.js:31` 在请求前调用 `setChatInput('')`，没有保留草稿。

证据：`compaction-result-1.json`、`compaction-result-2.json`、`08b-compaction-1.png`、`08b-compaction-2.png`、`08b-compact.log`。

建议：压缩动作不消费输入框；压缩参数使用独立字段。请求成功、无需压缩、失败和切换会话均保留对应会话草稿。补充压缩期间继续输入和异步响应返回后不覆盖新草稿的回归。

### F03 / P2：会话历史弹层遮挡重命名对话框

复现：打开历史列表，从行操作进入重命名，填写名称并点击“保存”。历史列表仍在上层，实际拦截保存按钮的点击。普通点击超时后再次用点击试探和 `elementFromPoint` 确认，命中的是 `.conversation-item-row`。先按 Esc 关闭历史列表，保存可以成功。

定位：`src/components/chat/ChatPanel.jsx:23` 打开重命名没有关闭历史；重命名对话框在面板内部，`RenameConversationDialog.jsx:16` 为 z320；历史 `AnchoredPopover.jsx:37` 默认 z430 且 portal 到外部。面板的 backdrop filter 还会影响 fixed 对话框的包含范围。

证据：`08b-first.log`、`08b-driver-review.png`、`08b-rename-overlap-confirmed.png`、`08b-compact.log`。

建议：进入重命名时关闭来源菜单，并将对话框放入统一的顶层 modal portal，统一弹层层级、焦点和 Esc 行为。回归覆盖鼠标保存、键盘保存、焦点恢复以及多种面板布局，不只提高一个 z-index 数字。

### F04 / P2：删除当前文件后，剩余标签与正文状态不一致

复现：同一编辑栏打开两份测试文件，删除当前文件。另一文件标签仍可见，但正文显示“当前文件已移入回收站”，没有自动显示剩余文件。点击剩余标签后恢复正常，磁盘内容完整。

定位：`src/hooks/editorToolRefreshActions.js:41` 的 `clearPathState` 过滤标签后直接关闭当前文件，没有选中并加载剩余标签。

证据：`05c-delete-active-other-tab.png`、`05c-delete-current.log`；用例 `W10-active-delete-tab-state` 和 `W10-other-tab-reopen`。

建议：删除当前文件时确定相邻的剩余标签并同步更新当前路径、内容、类型和状态；无剩余标签才显示空编辑器。需覆盖脏标签、多编辑栏、删除目录和异步加载未完成等情形，保留已有冲突保护。

## 首次失败与归因复核

- 首轮真实供应商请求遇到 TLS handshake timeout。UI 有错误和继续入口，实际继续后成功；这是外部连接失败，不算模型智力问题，也没有当成平台工具故障。仍保留初次失败日志和恢复事件。
- 自动化早期出现拖拽位置未命中、模型子菜单操作方式错误、用量入口文字错误、历史标题子串匹配分支、调用 Response.status 的方式错误等驱动问题，均保留首错并修正驱动复查。没有把这些初错计入四项产品缺陷。
- 后台任务首次查询错用不存在的顶层 conversation_id 字段，误记 MODEL_NOT_TRIGGERED；复核 payload_json 后找到了真实已完成任务，报告以实际任务/文件为准，保留旧记录以便追溯。
- 新建稿件撤销首次只等 5 秒便关闭浏览器，当时另一真实运行占用队列。复查服务 ready、文件和撤销日志：没有死锁、没有已执行撤销。空闲时通过 UI 重试，HTTP200、completed、新文件移入回收站且可恢复。因此不列为第五项缺陷；也未声称完成了 30 秒排队超时体验专项验收。
- 所有脚本的浏览器 pageerror 记录均为空。没有 pageerror 不代表 F01–F04 这样的状态和数据问题不存在。

## 建议修复顺序与未覆盖范围

先修 F01/F02 的输入持久性，再修 F03/F04 的交互状态；每项先添加对应故障回归，再实现并复测。采用明确消息身份、状态转换和文档路径，不使用正文关键词去猜测“是否已发送”或“是否完成”。这四项不需要先做大规模目录重构。

未测的范围包括云端 HTTPS/反向代理/SSE 超时、持久存储卷、真实服务重启与断电恢复、数据库/磁盘故障注入、长时间负载、大文档压力、多浏览器、多供应商组合和完整富文本语法矩阵。没有 Skill 不测试 Skill，未开启宿主命令，也不把云文稿工作台当成本地编码 Agent 验收。模型发现快加沿用之前专项记录，不新增测试配置污染当前设置。

目前结论是“主要文稿链路可运行，存在四项可复现平台缺陷”，不是“已完善、没有问题”。按本轮约定，问题先报告，产品修复留待后续确认。
