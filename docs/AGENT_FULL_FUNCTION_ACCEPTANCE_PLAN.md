# Perseus 全功能与 Agent 可靠性复验计划

日期：2026-10-23。状态：**用户已批准，2026-10-23 12:15 起执行**。批次 `20261023-1215`；实际结果另记，不将计划内容当作已通过。

这轮验收对象是服务器上的文稿工作台及其 Agent，不评价模型写作水平或推理能力。沿用 [既有 90 项清单](FINAL_ACCEPTANCE_PLAN.md) 的用例身份，重新在当前构建上验证，并补充本文件中的新功能与遗漏场景。此前 PASS 只作线索，不继承为本轮结果；此前“已修复”也不等于这次完整流程已通过。

## 一、模型报错怎么判

**上游失败本身不算 Perseus 缺陷；平台处理失败的方式仍须验收。** 每个场景分开记录“平台处理结果”和“目标操作是否完成”。例如模型返回 429 后，平台正确有界退避并诚实结束，可以判错误处理 PASS，但被中断的文稿生成步骤仍记 BLOCKED，需用可控模型补测，不能整条直接算通过。

| 现场情况 | 归因和验收方式 |
| --- | --- |
| 上游 401、429、5xx、超时、断流、服务不可达 | 不因上游错误扣平台分；检查错误可见、重试有界、可取消、终态正确、已有内容不丢、后续可重新运行 |
| 模型用错工具参数、调用不存在的工具 | 模型行为单列；平台须明确拒绝、返回可用错误，不误执行、不写坏数据 |
| 模型反复读同一文件、无新信息地重试、缺少完成协议 | 不评价模型智力；检查平台能否有界停止、可取消并如实报告，不将写入成功自动等同整轮成功 |
| 平台给出的 schema/工具清单错误，合法工具请求被误处理 | 平台 FAIL，即使现象表现为模型“不会用工具” |
| 模型声称改好了但未写文件 | 对照落盘和工具记录；模型声明单列，验证平台完成校验是否拒绝无依据成功，不仅凭回复用词判定 |
| 本轮附件未进入下一轮、搜索错误没送回模型、后台拿错历史 | 平台 FAIL，不能归为模型能力不足 |
| 模型写得一般、偏离语气、事实推理不佳 | 不评分；只查输入材料/约束是否实际送达、工具契约及结果处理是否正确 |
| 模拟服务或测试脚本用错协议、字段或拖错对象 | 测试驱动问题，保留首次现场，修正驱动后重测；不报成产品缺陷 |

## 三、执行顺序

1. **冻结基线并建立功能清单**：核对当前 UI 入口、API 路由、模型可见工具/文本编辑协议与权限；每个可用功能映射用例。旧清单外的能力现场补项，不静默遗漏。核对空闲状态，备份、哨兵和原数据摘要。
2. **自动基础回归**：前端单测、Go 全包和 vet、UI/结构门禁、前后端构建、完整浏览器套件。对跳过、平台不支持与驱动错误分别记录，不刷测试次数直到偶然全绿。
3. **正常功能遍历**：独立实例实际浏览器 + 实际后端 + 本地可控供应商；正常工具结果必须来自真实执行器/文件系统，不能只 mock 页面接口冒充端到端通过。UI 时序专项可单独拦截接口并明确标注层级。
4. **8080 真实文稿流程**：执行下一节主线，逐条检查所有可观察回复及其实际工具/文件效果。上游故障记录后转向不依赖它的项目，不反复换提示词掩盖问题。
5. **隔离故障与恢复**：覆盖前台/后台、持久化、取消、并发、网络中断、崩溃和恢复；一次只改变可识别的故障条件，保留首次失败。
6. **持续运行与交叉操作**：90 分钟混合运行；包含持续浏览器操作和后台核对，不用单纯 API 循环冒充 UI 长时运行。结束检查任务、队列、连接、事件增长和数据完整性。
7. **收尾报告**：按功能和风险分别给结论。发现产品问题先留证，不在测试基线上无记录地边测边改；修复进入新构建，再复测缺陷及受影响路径。

本地预计约 4–6 小时，实际视故障调查而定；云端另列。确认后由我准备材料、测试账号、模拟服务、脚本和审阅记录。没有新发现或新证据时不制造额外修改。

## 六、重点补齐旧缺口和新变更

旧验收的 19 个本地未完整覆盖项全部重新拆成子场景：M01/M04/M05、F06、E04/E05/E10、C05/C06/C09、R06、T04、D05/D07/D08、O03/O05/O06/O07。后续已有专项结果可以辅助定位，但本轮仍要在指定构建上执行。

重点证据要求：

- **参数送达**：界面选值→保存/重开→实际供应商请求；不只检查下拉框能打开。
- **异步竞态**：A/B 文件读请求乱序、输入后立刻切/关标签；格式修复确认期间切文件、冲突、保存失败；确认没有写到错误目标。
- **消息交互**：自由回答/选项回答、上翻不被流式强拉底部、再次跟随、跨会话草稿/附件；刷新前后分别检查。
- **事件流**：两个隔离浏览器同时打开同一运行；断网/重连与超过 200 条事件叠加；检查 seq/游标无遗漏，重复重放不重复副作用。
- **后台极限与重启**：修复耗尽后诚实结束；在后台实际运行时强杀隔离进程并重启；不把前台崩溃结果代替后台结果。
- **正常停机**：区分受支持的优雅退出与强杀；Windows 无可用信号途径时记限制，不能用 `Stop-Process` 充数。
- **恢复后的可用性**：恢复匹配备份后真正登录、读写、开新任务，并从 UI 对可撤销变更操作；非只读摘要比对。
- **全程错误观察**：从浏览器启动开始收集 console/pageerror/请求失败；注入的预期错误与非预期错误分别列出，导出检查不含凭据。

## 七、Agent 故障组合

采用可控供应商脚本，经真实 HTTP 请求触发 Agent，核对出站尝试次数及间隔、请求内容、工具台账、事件和文件效果。正常结果和故障结果都需要对照组。

| 注入点 | 必测处理 |
| --- | --- |
| 工具前上游 401/429/502、EOF、截断/空回复 | 正确分类和有界退避；原错误保留；无假成功；下一次正常请求仍可运行 |
| 首次写入后下一轮上游失败 | 已写成果保留；未做部分如实可见；继续不重放已确认写入；预算不被无限重置 |
| 重复工具 ID/重复请求、丢受理响应 | 对照项目支持的幂等身份，不能重复写入/创建任务；不依赖正文关键词去重 |
| 无效参数、缺文件、旧哈希、多文件部分失败 | 错误回到模型、非目标文件保持；回滚不覆盖后来的人工版本 |
| 无进展循环与有效重复复核 | 前者有界退出/可取消，后者在文件版本或结果更新时不被误杀 |
| 受理/排队/供应商请求/工具在途/终态竞争期间取消 | “请求停止”与“已经停止”分清；稳定终态后不启动新副作用；已发生的在途效果如实记录 |
| 事件/成功终态/后台转交持久化失败 | 事务回滚/诚实失败/幂等恢复符合契约；不能重复终态、重复后台任务或丢检查点 |
| 断线、刷新、重启和显式继续 | UI 与持久状态重新一致；不以恢复为由自动重放不确定副作用；后台没有能力恢复时明确中断 |

## 八、逐条回复和后台审阅

审阅所有可观察的助手正文、提问、进度段、被终态替换的正文、后台逐轮正文与最终消息。流式片段先组装，不把每个 token 算一条；分支复制、重放、任务预览建立关联，不重复计数。不声称看到模型未公开推理。

每条记录：当前要求、正文、身份、是否有实际进展、所声称读写/完成/错误对应的证据，以及正常/合理等待/已恢复异常/疑似绕圈/声明不实/证据不足。不能仅按“失败”“完成”等关键词判断。重复调用需对照参数、版本、结果和有效进展。

连续三次等价无进展动作触发人工调查；连续五分钟没有新正文、工具结果、文件变化或可解释等待时保存现场并检查。合理退避和等待用户回答不算绕圈。这是测试看护规则，不修改产品阈值。

## 九、通过条件和交付

用例分别记 PASS / FAIL / BLOCKED / NOT COVERED / N/A，并记录平台/上游/模型/驱动/证据不足归因。复合用例有一个要求未完成就不能整项 PASS；功能不存在但属于批准范围不能偷改为 N/A。

本地核心通过要求：工具执行和文件效果一致、数据不丢不串、用户隔离、取消/恢复、输入只消费一次、前后台终态与事件一致、错误有界可见、后续可继续使用。数据损坏、越权、凭据泄露、不可控执行、假成功和核心阻断均阻止对应范围通过。

交付 `docs/AGENT_FULL_FUNCTION_ACCEPTANCE_RESULTS.md`：功能覆盖矩阵及子场景、原始失败/修复后复测区别、逐条回复审阅覆盖率、后台状态核对、外部故障清单、未覆盖项、缺陷优先级与复现证据、请求/资源记录及原数据完整性。私有证据放 `_local_artifacts/agent-full-function/<批次>/`。旧报告保持原样。

结束核对所有本轮运行/任务/队列/待发输入；失败和检查点要有明确归属，不把正在工作的用户任务当测试残留取消。关闭隔离服务，保留证据。没有待交付修复时不重启 8080；如后续更新则先确认空闲并另行备份。
