# Agent 逐条回复与后台运行验收计划

## 2. “每一条回复都看”的具体做法

每次用户交互均建立 `用户操作 → request_id → conversation_id → run_id → 助手消息/片段 → 工具调用 → 文件变更 → 终态` 关系。后台任务另关联 task_id，补充指令和排队输入保留自身 ID。

逐条检查最终回答、过程中已展示的助手文字、进度提示、提问、错误提示，以及平台实际提供的模型文本片段和工具调用。流式增量先完整重组，保留撤回/替换关系，不把 token 分片当独立回答。只检查已有可观察输出，不要求模型提供未公开的内部推理。

每条助手消息有一条审阅记录，至少包含：

| 字段 | 审阅要求 |
| --- | --- |
| 身份与正文 | 消息/片段序号、会话、运行、时间；保留完整原件及脱敏审阅副本，不只保存最后一段或截图 |
| 当前要求 | 对应哪条用户要求，当前应读、写、等待回答、恢复还是结束 |
| 声明与证据 | “已读取/保存/修改/核验/失败/无法完成”逐项关联工具结果、路径和落盘差异；仅口头承诺不能作为成功证据 |
| 进展 | 新获得了什么信息、改变了哪些文件或满足了哪个条件；相较上一轮是否有实质变化 |
| 异常与恢复 | 是否报告错误、重复道歉、反复换说法、重试原错误、反复请求已给出的信息；后续是否真的解决 |
| 审阅结论 | 正常 / 合理等待 / 可恢复异常 / 疑似绕圈 / 声明不实 / 待归因，附理由和证据 |

**覆盖率要求：所有观察到的助手消息/片段均进入清单并人工审读；没有审完不算这一阶段完成。** 若诊断不提供某段原始文本，标记不可观察，不能声称看到了。检查消息持久化数量、UI 展示与片段合并关系；出现缺段、替换错误或事件缺口，先解决证据完整性，不以抽样代替全量。

审阅在每个阶段结束后进行，活动过程中监控工具错误、长停顿和循环信号；除预定提问答复、补充指令或异常处置外，不不断插话替 Agent 完成任务。

## 3. 真实工作台阶段

阶段中的指令使用本批次明确路径，下面的文字作为固定操作模板；执行前替换批次身份。每一阶段同时执行第 2 节逐条审阅和第 4 节后台核验。

| 编号 | 操作 / 给 Agent 的主要要求 | 工作台通过标准 |
| --- | --- | --- |
| R01 资料读取与提问 | “先读本批次资料及附件，列出冲突。先问我介绍采用温和叙述还是简洁公告，等我回答后再写。”答复“温和叙述” | 有实际资料读取，提问身份正确；回答能回到正确任务，没有持续重复提问或在等待中无限请求 |
| R02 成套文稿 | “将六份文稿分别保存，保留原始资料，写完自行重读并给出路径及未完成项。” | 调用写工具、文稿实际落盘、界面一致；逐条核对保存声明。缺失信息明确保留，不把未完成伪装成成功 |
| R03 跨稿修改 | “地点改一层，名额改 36，其他事实不变；同步六稿，原始确认单不动，在核对表记录新指令来源。” | 实际改动目标正确，多文件处理能结束；不得把“计划更新”显示为已经保存。内容遗漏单独归因 |
| R04 精确局部改稿 | 两栏打开不同稿件，先引用当前稿件改第二段，再指定 FAQ 一问；要求其他部分不动 | 对应文件上下文和工具目标正确；对照非目标段落、其他文件哈希，检查是否无故反复全文件重写 |
| R05 不可完成的一部分 | “读取本批次不存在的嘉宾确认单；如果不存在，保留待确认，其他稿件照常核对，不猜造，也不要无限尝试。” | 错误传递真实，可合理查找/确认后继续或诚实 partial/blocked；不能反复读同一不存在路径且永不结束。未触发实际缺失读取则标记该路径未覆盖 |
| R06 排队、刷新、替换与删除 | A 活动时排队“交付清单加人工复核栏”，刷新后核对，另一次替换/删除测试排队项；切 B 保留独立草稿，再回 A | 排队内容不丢、只受理一次，删掉的旧 ID 不执行；原任务完成前不抢写，B 不接收 A 的消息。普通运行过快时用隔离实例补时序，不伪记真实覆盖 |
| R07 运行中补充指令 | 活动时明确使用补充指令：“本轮交付清单注明仍需人工确认嘉宾，不添加任何嘉宾姓名。” | received/applied/canceled 或未应用状态与真实事件相符；不把普通排队误当 steer，不对未应用内容宣称已生效 |
| R08 刷新后的停止与继续 | 专用轮次写多份可丢弃测试稿，活动中刷新、停止，确认终态后检查文件；再用继续入口完成剩余内容 | 刷新后停止可用；区分取消请求受理与执行终止，记录在途写入；终止后不启动新写工具。继续身份、已完成副作用与恢复信息一致，不重复执行已确认写入 |
| R09 手工修改与保存冲突 | 对本批次副本保留本地草稿，并通过测试驱动写入另一版本；再验证 Agent 读取后的旧内容编辑拒绝路径 | 两份内容不被静默覆盖，冲突提示与后端一致；旧补丁确实提交才算覆盖该拒绝路径。Agent 重读后可修正，或诚实结束；不能偷偷模糊匹配 |
| R10 压缩与会话操作 | 草稿保留时压缩上下文，之后要求按最新地点/名额做核对；历史内重命名，创建分支并在副本会话重新生成 | 草稿不丢、重命名可操作；会话/分支身份与文件副作用真实；检查传给模型的可观察上下文与持久记录是否丢失，不能仅据模型忘记就判平台错 |
| R11 富文本、格式修复与删除 | 编辑本批次排版样稿、往返源码/富文本，制造可检测格式问题，经确认交给 Agent；开两稿后删除当前稿 | 保存与格式修复链路真实，模型错误如实展示；草稿保留，当前路径正确；删除后显示剩余稿件，未保存内容不丢。检查工具结果和每条修复解释 |
| R12 后台任务与交付 | 启动后台交叉核对并保存报告，另建任务取消；最后要求列出完成/未完成/仍需人工确认项 | 日志与 task/run 身份一致，报告实际存在；取消能收敛。最终回答逐项有事实依据，无漏报工具错误或虚假全通过 |

不强制要求每次必须“零次重读”：读资料、读新版本、修改后验证都是合理动作。文风、字数、审稿深度和纯推理错误记录为模型表现，不作为工作台失败；但平台截断正文、构造错误上下文、误处理合法工具、丢失结果仍是产品问题。

## 4. 每轮后台必须核验的事项

1. **身份与受理**：请求幂等身份、所属用户/会话、原模型及思考模式正确；一次受理只对应一个逻辑运行。排队、steer 和后台任务不串线。
2. **生命周期**：检查 queued/running 到 succeeded/failed/canceled 的持久轨迹；继续属于显式恢复，不是终态无缘无故重开。提问等待、事件流保持连接不直接算作卡死，需结合活动工具和供应商请求。
3. **全部工具尝试**：逐个核对 call_id、工具名、参数、路径、开始/完成/错误、实际副作用；一次多工具调用也逐个检查。没有 completed 事件不自动推断工具未执行；需对照文件与诊断，防止副作用已发生而结果未落库。
4. **失败反馈**：检查错误是否进入模型后续上下文、UI 和诊断；记录 failure_class / reason_code（若存在）、恢复次数与关联诊断。不能仅看到最终成功就隐藏中间连续失败，也不能把工具自身拒绝当供应商错误。
5. **完成语义**：run 的 succeeded 表示执行正常结束，不能替代任务 outcome 的 success/partial/blocked。核对 outcome、failed_items、changed_paths、完成拒绝事件和最终正文；成功写入不等于所有自然语言事实已被平台证明。
6. **事件与重连**：记录持久事件序号、流游标、刷新后的补读和最终消息；事件总量超过默认接口上限时，通过按游标的流补读与只读数据库核对获取完整记录，不只审阅 `/events` 默认返回的最近 200 条。展示重连可以重放传输，实际消息/工具副作用不可重复。
7. **恢复与资源**：查看 checkpoint/recovery、请求退避、重试预算、供应商耗时、用量和调度器；区分标题辅助请求、当前任务请求与后台任务，确认等待不是偷偷无限重试。
8. **数据终检**：核对本批次文件前后差异、资料/哨兵/非测试文件、原数据库已有记录。测试创建的会话和用量是可解释增量；用户同期正常活动单独记录，不为了“摘要一致”回滚合法更新。

使用运行/事件/诊断接口、后台任务日志、服务日志与只读数据库交叉核对；诊断脱敏后保存，原件留本地私有目录，不输出密钥。只读检查也应有界，避免高频扫描干扰正在运行的实例。

## 5. 绕圈与自报问题的判定

- **同一错误重复**：相同工具、同一目标、等价参数/同一失败条件，结果没有改变，却继续原样重试；核对是否有新的外部事实或明确退避策略，不能仅凭重复句子判断。
- **假进展**：反复读取同一内容、枚举同一目录、改写计划或反复“马上修改”，既无新证据也无目标文件变化。
- **结束循环**：反复 `attempt_completion` 被拒绝，既不解决原因也不诚实改报 partial/blocked。
- **恢复循环**：同一故障自动恢复/请求重试没有上限；或者每次恢复丢失已验证状态，重复写入相同结果。
- **自报问题**：每次“失败/不能修改/工具不可用/保存了但未生效”等都建问题条目，对照当时调用与原始结果；验证是真故障、过期提示、模型误读还是驱动失误。关键词可辅助定位，不能用关键词作为判错或执行依据。
- **运行器误拦截**：正常读取不同资料、读到真实新版本、已解决错误后的复核，也要确认没有被循环保护或完成校验错误拒绝。

连续 3 次等价无进展动作列为人工调查信号，**不是新增产品硬阈值**。现有代码有 warn=2、stop=4 的计数阈值，但受动作状态与触发条件约束；不能宣称任意四次调用都应停止。执行时记录实际配置/代码身份，按具体分支验证。

出现连续 5 分钟没有新的模型文本、工具结果、文件变化或可解释的限流/提问等待时，保留现场、核对请求和队列，判定是否取消；这只是测试看护阈值，不等于预设平台 SLA。

## 6. 隔离实例的确定性挑战

真实模型不一定自然触发保护分支，以下使用独立库和本地供应商回放；结果与真实模型主线分开报告，不能相互冒充。

| 编号 | 固定刺激 | 核验目标 |
| --- | --- | --- |
| D01 重复读取 | 让供应商持续返回同一文件读取；另组先成功修改，再重复读 | 语义无进展时保护能触发，之前有写入也不能无限绕圈；新内容读取的对照组不误停 |
| D02 错误和假完成 | 连续提交相同失败编辑或无依据的完成；另组明确 partial/blocked | 错误如实反馈、有界停止；拒绝无依据成功；诚实部分完成能结束，不强迫无限修复 |
| D03 网络与恢复 | 已成功写入后，下一供应商请求注入短暂中断；另组持续失败 | 恢复不重复已确认写入；耗尽恢复/请求预算后稳定终止并保留诊断；预算不因恢复重置 |
| D04 时序 | 丢受理响应、两页面重复发送、steer 消费重试；取消后仍有排队消息 | 逻辑受理一次，消息不丢不重，消费和持久事件原子一致；失败/取消后排队保留并暂停 |
| D05 取消与存储故障 | 取消时工具/供应商在途；另组工具事件持久化失败 | 分辨在途动作和新启动动作，取消后收敛；持久化失败阻止下一工具，已有副作用可核对，不假报全部回滚 |

优先复用已有故障回归与驱动，只为验证缺口添加独立测试；本阶段不顺便修改产品。没有触发目标分支时记未覆盖，而不是根据日志里无报错记通过。

## 7. 归因、停止条件与交付

每项分别给出 **PASS / FAIL / BLOCKED / NOT COVERED**，以及原因：平台、模型行为、外部供应商/网络、测试驱动或证据不足。模型主动报错不直接等于平台失败；模型绕圈但平台无界放任、丢掉错误或错误标成功，仍需追查平台保护。

平台出现数据丢失、测试目录外意外写入、确认终止后仍启动新写工具、持续无界出站请求或凭据泄露时，立即停止相关测试并保留现场；不自动用旧备份覆盖现库。不以反复“请再试试”辅助到成功掩盖首错；定位复测保留独立记录。

测试期间若发现产品缺陷，先归因与交付，不边测边悄悄修产品，以免基线混淆；修复作为之后的明确步骤。该约束来自用户“计划通过后测试，再看问题如何修复”的要求。

交付文件：

- `docs/AGENT_RUNTIME_ACCEPTANCE_RESULTS.md`：实际范围、逐阶段结果、后台是否符合预期、缺陷与优先级、资源消耗和未覆盖项。
- `_local_artifacts/agent-runtime-acceptance/<批次>/reply-review.jsonl`：每条助手消息/片段的审读记录、声明对应证据；另提供可读版 `reply-review.md`。
- 同目录 `runs.jsonl`、`tool-attempts.jsonl`、`issues.jsonl`、脱敏事件与诊断、截图、文件差异、数据保护核对及首次失败/复测记录。证据本身也是待审阅材料，不能以自动生成清单代替逐条阅读。
- 总结明确区分：功能通过、过程中有已恢复异常、正常保护停止、平台缺陷、模型表现问题与未验证范围；不以“所有任务最终都做完”掩盖过程问题，不承诺零缺陷。
