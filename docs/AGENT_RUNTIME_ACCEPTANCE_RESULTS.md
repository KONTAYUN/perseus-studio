## 4. 两项确认的产品问题

### AR-01 · P2 · 任务转交缺少统一持久完成事件

两个真实运行的数据库状态都是 succeeded/completed，但没有 `run_completed`：

- `run_1792663615294049900_1413`：35 条持久事件，最后是附任务身份的创建回执。
- `run_1792663662261723000_1468`：28 条持久事件，同样止于创建回执。

[转交路径](../backend/internal/api/conversation_run_task_completion.go) 创建任务、保存回执后直接发布成功状态；[普通完成路径](../backend/internal/api/conversation_run_completion.go) 会另外追加 `run_completed`。后台转交动作也没有普通工具一样的完整开始/完成生命周期。

实际 UI 可依据状态快照正常结束，任务创建和报告也真实成功，**没有复现界面卡死或任务丢失**。问题在于终态事件契约不一致，按事件重放、诊断或统计的消费者无法统一判断结束。

建议：让普通完成和后台转交共享终态收敛规则；终态保存 outcome/转交语义、task_id 与最终消息身份，并给转交动作补可关联事件。回归覆盖正常转交、存储失败和重放；创建任务与终态之间崩溃是否重复创建，需另行故障注入，不能据本次缺事件直接声称已复现重复。

### AR-02 · P2 · 后台任务中间回复和结构化轨迹丢失

真实核对任务 `task_1792663631842868900_1455` 有 4 个模型轮次、33 条简化日志、3 条完整工具记录；只保存最终助手正文。任务关联的 1 条 `agent_events` 是前台创建回执，**不是后台四轮运行轨迹**。

[后台事件回调](../backend/internal/tasks/manager_ai_helpers.go:78) 把事件映射为少数日志文本，丢掉模型增量/完成正文以及请求尝试、恢复、循环保护等结构化载荷。[最终消息与任务结果](../backend/internal/tasks/manager_ai.go:118) 使用空 meta 保存正文，result 只有通用 ok/会话/完成文字，没有保留 reply.outcome 等信息。

因此可以核验真实读写、报告和最终说明，无法逐条检查后台中间文字是否自报问题、绕圈或被纠正。最终正文也没有直接的 task_id 元数据，需要通过工具附件/任务时间关联。**没有实际复现 partial 被错误标作完全成功**，这里只确认 outcome 信息未保留以及对应风险。

建议：后台执行保存可重放的结构化事件及可观察回复片段，记录 task/run/工具身份、请求次数、错误原因、恢复/修复轮次和 outcome；后台取消也保存明确终态。补“中途文字 → 工具失败 → 恢复 → 最终 partial”和取消的隔离回归，再复测本次后台任务。

两项原始证明见 [observability-proof.json](../_local_artifacts/agent-runtime-acceptance/20261022-1747/observability-proof.json)，问题清单见同目录 `issues.jsonl`。
