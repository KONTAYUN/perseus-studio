# Markdown 修改失败诊断与修复

2026-10-20 晚间，用户截图诊断 ID `diag_1792506384614233900_77`。

## 已确认原因

这次不是文件写权限或 HTTP 连接失败。运行账本显示：一次成功的 `read_workspace_text`，随后三次 `apply_workspace_patch` 匹配失败；第一次补丁较大，后两次重复同一小补丁。全部失败于 hunk 1，未进入文件写入。

读取结果中的真实 `&` 被 Go 默认 JSON HTML 转义编码为 `\u0026`，再作为字符串嵌入供应商请求。模型把这一表示写进补丁旧文本，和磁盘里的 `&` 不同。此外，模型用补丁行 `-` 试图删除文件中孤立 `-`，但该补丁行表示删除空行，删除真实 `-` 应写 `--`；相邻空行也必须按实际范围匹配。这些原因叠加造成安全校验拒绝。三次停止保护生效，旧错误提示却笼统要求检查供应商参数，误导定位。

## 变更

- AI 内部模型 JSON 编码关闭 HTML 转义；工具输出、预算重新编码、上下文读视图重编码共用编码器。仍保留 JSON 必需的引号/反斜杠转义，且不做字符串全局反转义，避免损坏原文件里真正的 `\u0026`。外层 HTTP JSON 编码保持原协议。
- 旧检查点中的读取结果在供应商观察边界也重新编码，确保恢复旧失败会话时不用继续携带容易被误抄的 HTML 转义表示；仅改变 JSON 表示，不修改存储的原文或会话历史。
- 在提示词和 patch 失败结果里明确：JSON 转义和行号不是原文；解释删除空行与删除字面 `-` 的区别；重新读目标窗口，使用更小补丁，禁止原样反复提交。
- patch 匹配失败达到限制时，用户提示改为“补丁与当前原文不匹配”，保留停止保护和原有匹配、并发哈希检查。没有将错误补丁模糊套用到文件。
