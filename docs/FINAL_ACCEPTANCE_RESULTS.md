## 已确认问题

### FA-01 · P1 · 上传附件跨提问轮次丢失上下文

真实流程先上传文本附件并要求提问确认语气。首轮附件 metadata 为 included_in_context=true；回答语气进入下一轮后，Agent 多次寻找附件，最终如实报告无法核对。不能仅据模型这句话判断原因，因此在独立库/本地供应商实际捕获两轮 HTTP 请求复现。

确定性结果：附件专有标记只存在于文件正文、未写进用户提示。第一轮供应商请求包含附件全文；回答提问后的第二轮请求完全不含该正文。历史消息只保存附件 metadata；`messages.go` 只把本次 AttachmentPayload 加到最新用户消息，后续新轮无原附件正文可恢复。

证据：`attachment-wire-proof.json`，对应独立测试会话与两个 run_id 在文件内；真实观察见 `live-evidence.json`。这是平台上下文持久性问题，不能归为模型智力不足。本轮保留原始失败，不在基线上修复；附件跨轮能力不能通过。

### FA-02 · P1 · 后台转交持久化故障后继续会重复建任务

在恢复到 18086 的私有副本中，先禁用并替换复制的所有真实模型/搜索凭据，再注入 SQLite trigger：只拒绝 task_handoff_completed 事件写入。此时任务已经落库，前台如实进入 failed。移除 trigger 并显式继续同一 run 后，平台再次创建后台任务，两个 task 的 payload.source_run_id 完全相同。

证据 `handoff-gap-proof.json`：source run `run_1792680662041900800_6`，产生 `task_1792680662113734700_34` 和 `task_1792680662197346300_49`。本次精确复现的是**任务创建后的事件存储失败窗口**，不是在该窗口强杀进程。两个任务实际写同一稿件的后果尚未触发，不把潜在风险写成已发生的数据损坏。

建议将任务创建、source run 关联、转交回执与终态作为可恢复事务；source_run_id 加所有者范围内的幂等约束，继续时先查询已有任务并补交接，不重新执行创建。仅保证 run_completed 原子写入不能覆盖这个窗口。
